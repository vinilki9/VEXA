# VEXA Taxi + VEXA MAP 0.3.2 — аудит совместимости Client / Backend / Driver

**Дата:** 21 ноября 2026 г.  
**Исходная версия:** VEXA_TAXI_LOCAL_MAP_INTEGRATION_0.3.1.zip  
**Назначение:** обновлённая локальная копия исходного кода для Android Studio и Docker. Не готовый APK и не подтверждённая работа всей системы на компьютере пользователя.

## Подтверждённые проблемы и исправления

1. **Driver → Backend: ошибочный тип `order_id`.** Обработчик `POST /api/v1/driver/orders/{order_id}/status` использовал `order_id: str`, хотя `Order.id` — `Uuid(as_uuid=True)` в SQLAlchemy. На SQLite обработчик UUID-поля действительно не может привязать строку (`AttributeError: 'str' object has no attribute 'hex'`), что может приводить к ошибке при изменении статуса поездки. Параметр обработчика заменён на `UUID`; FastAPI теперь валидирует входной ID до вызова обработчика. Разрешённая серверная цепочка осталась прежней: `assigned → arrived → in_progress → completed`.
2. **Client → Backend: статус поездки зависел от первых 50 заказов.** Вместо поиска текущей поездки в `GET /api/v1/passenger/orders` введён защищённый `GET /api/v1/passenger/orders/{order_identifier}`. Поддерживаются UUID и публичный номер заказа, обязательна пассажирская авторизация, поиск фильтруется по `Order.passenger_user_id`. Android Client теперь опрашивает именно этот маршрут. Тест на реальной временной SQLite-базе подтверждает: свой заказ доступен по обоим идентификаторам, чужой возвращает 404.
3. **Driver: завершение заказа и обновление кошелька были связаны в одну успешность.** Если `POST` уже подтвердил завершение, а последующий `GET /wallet` падал, интерфейс ошибочно сообщал о провале операции. Теперь сбой чтения кошелька не отменяет успешное завершение; баланс обновится отдельно. При сетевой ошибке изменения статуса выполняется повторное чтение активных заказов, поскольку ответ мог потеряться после серверного сохранения.
4. **Backend: дублирование определений ценового предложения.** Два одинаковых определения `PRICE_QUOTE_TTL_MINUTES`, `build_price_quote_fingerprint` и `create_price_quote_token` сведены к одному набору без изменения формата подписанного токена и расчёта в копейках.
5. **Client: зафиксирован один город в исходнике.** `city_code` теперь берётся из Android BuildConfig `VEXA_CITY_CODE`, задаваемого через `vexaCityCode` в `gradle.properties` (по умолчанию `obolensk`). Это конфигурация сборки, **не** полноценный интерфейс выбора города. Аналогичная настройка добавлена в Driver для единообразной конфигурации, при этом фактический город Driver по-прежнему определяется профилем на Backend.
6. **Driver: локальная проверка перехода статуса.** Неподдерживаемые значения статуса отсекаются до HTTP-запроса; сервер остаётся источником истины и проверяет текущий статус сам.

## Что фактически проверено

- **47 тестов Backend/контрактов** прошли (`47 passed, 14 subtests`): 42 исходных профильных теста тарифов/маршрутизации плюс 5 новых тестов совместимости. Один тест динамически исполняет *исходную функцию нового защищённого API* в изолированной среде на настоящих таблицах SQLAlchemy/SQLite; это не HTTP-тест полного FastAPI-приложения.
- **11 тестов VEXA MAP** пройдены, включая региональные растровые MBTiles, поиск, маршруты без OSRM и проверки прокси.
- **23 адреса мобильных API** в коде Client/Driver сопоставлены с объявленными путями Backend статическим тестом. Полной проверки соответствия каждого поля JSON и сценариев реальных пользователей не было.
- Проведена проверка синтаксиса Python, целостности ZIP и соответствия обновлённого манифеста файлов.

## Ограничения и незакрытые риски

- **Полный набор backend-тестов не выполнен**, поскольку здесь нет части зависимостей из `backend/requirements.txt`, в частности `python-jose` и `passlib`, а установка через интернет недоступна. Это ограничение тестовой среды, а не подтверждённый дефект кода.
- **Gradle Sync, APK, запуск Android Client/Driver, E2E API с авторизацией и PostgreSQL/Docker не выполнены**: здесь нет Android SDK, рабочего локального ПК пользователя и подготовленного тестового окружения с учётными записями.
- На местном компьютере всё ещё потребуются PostgreSQL, Redis, сервис VEXA MAP и граф OSRM с реальными данными, SMS-провайдер для пассажирского входа (или отдельный тестовый режим), LAN IP и тестовые пользователи.
- Backend пока не поддерживает автоматический выбор филиала при нескольких активных филиалах города; такой заказ может вернуть 409. Эта бизнес-функция не изменялась, так как требует согласования логики распределения заказов.
- Динамический выбор города пассажиром и восстановление поездки после переустановки приложения не реализованы полностью. Не следует считать проект готовым к эксплуатации по всей России.
- При выпуске release APK нужен HTTPS и проверка Android сетевой политики. Локальный debug HTTP нельзя выставлять наружу.

## Повторная проверка

Из корня `VEXA-deploy` после установки зависимостей для Python:

```bash
PYTHONPATH=backend python -m pytest -q \
  backend/tests/test_mobile_integration_contract.py \
  backend/tests/test_pricing.py backend/tests/test_routing.py \
  backend/tests/test_routing_providers.py backend/tests/test_route_pricing.py
python -m unittest discover -s VEXA_MAP/tests -v
```

После этого на локальном ПК — `docker compose -f infrastructure/docker-compose.yml up -d --build`, миграции БД и реальный сквозной тест заказа: авторизация пассажира → предварительная цена → создание заказа → предложение водителю → принятие → прибытие → начало → завершение → проверка заказа у пассажира и кошелька водителя.

**Оригинальный архив 0.3.1, GitHub, VPS и личный компьютер пользователя не изменены.**
