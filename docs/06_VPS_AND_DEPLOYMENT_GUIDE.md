# 06. VPS и инструкция развёртывания VEXA

## Целевой сервер (настройка проекта без подключения)
- ОС по сведениям пользователя: Ubuntu.
- Адрес VPS: `109.120.184.20`.
- Планируемый публичный адрес API: `https://109.120.184.20`.
- Домен пока не предоставлен.

**Ограничение выполненной работы:** конфигурационные файлы проекта подготовлены под указанный адрес. К VPS не подключались, команды на сервере не выполнялись, состояние ОС/портов/Docker не проверялось. Нельзя считать, что Backend, PostgreSQL, Redis, Nginx или HTTPS уже установлены либо запущены.

## 1. Что подготовлено в проекте
- Android Client: базовый адрес изменён на `https://109.120.184.20`.
- Docker Compose: порт Backend опубликован только на `127.0.0.1`, чтобы не выставлять порт приложения напрямую в Интернет; предполагается доступ через Nginx.
- `.env.example`: добавлен `VEXA_PUBLIC_API_URL` как ориентир конфигурации.
- Nginx: пример проксирует `/api/` и `/health` на локальный Backend `127.0.0.1:8000`.
- Dispatcher и Driver пока не имеют полноценной интеграции с API; добавление адреса в конфигурацию само по себе не подключает их к Backend.

## 2. Важные ограничения перед запуском
1. Backend в текущем комплекте — демонстрационный FastAPI starter: `/health` возвращает `demo`, а создание заказа не сохраняет заказ и не назначает водителя.
2. Client сейчас вызывает `/api/orders`, а Backend предоставляет `/api/v1/orders`. Контракт запроса и обязательный заголовок `Idempotency-Key` также требуют согласования. Поэтому смена IP не делает создание заказа рабочим.
3. `https://109.120.184.20` — заданный пользователем целевой URL, но наличие HTTPS-сертификата для IP и доступность адреса не проверялись. Для production предпочтительно дождаться домена, направить DNS A-запись на `109.120.184.20` и выпустить сертификат для домена.
4. Не заполняйте `.env` паролями-заглушками. Создайте уникальный длинный пароль и храните `.env` только на сервере.
5. Не открывайте PostgreSQL/Redis в Интернет. Порт Backend в Compose привязан к loopback; наружу должен смотреть только настроенный reverse proxy.

## 3. Будущий порядок развёртывания (после отдельного разрешения)
1. Сначала получить разрешение на подключение и read-only диагностику VPS.
2. Проверить Ubuntu, дисковое пространство, Docker/Compose, занятые порты и существующие службы.
3. Сделать резервные копии текущих данных и конфигурации, если они есть.
4. Согласовать домен и HTTPS; подготовить Nginx TLS-конфигурацию.
5. Подготовить production `.env` с надёжными секретами.
6. Доработать Backend до production: авторизация, tenant isolation, БД, миграции Alembic, сохранение заказов, диспетчеризация, аудит и тесты.
7. Согласовать API-контракт и подключить Client, Driver и Dispatcher.
8. Развернуть сначала тестовое окружение, выполнить проверки и только после подтверждения — production.
9. Настроить резервное копирование и процедуру отката.

## 4. Что не выполнялось
- SSH/консольное подключение к VPS.
- Проверка доступности IP, портов, служб или состояния Ubuntu.
- Установка/обновление пакетов, Docker, PostgreSQL, Redis или Nginx.
- Изменение firewall, DNS, сертификатов, systemd или файлов на сервере.
- Запуск контейнеров, миграций или перезапуск сервисов.
