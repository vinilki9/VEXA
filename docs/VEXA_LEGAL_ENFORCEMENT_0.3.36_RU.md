# VEXA Legal Enforcement 0.3.36 — локальная интеграция

## Что теперь подключено

Серверная проверка `legal_eligibility` запускается в **трёх** местах: при выборе кандидата для автоматического предложения, при ручном назначении диспетчером (`save_driver_assignment`) и при принятии водителем ранее выданного предложения. Запрет действует, если отсутствует актуальная запись по **паре водитель–автомобиль**. Для заказа с детским креслом дополнительно требуется подтверждение его наличия.

`LEGAL_DISPATCH_ENFORCEMENT=true` — значение по умолчанию. В разработке явно можно указать `false`, но в `production` это вызывает ошибку запуска. **С включённой проверкой имеющиеся тестовые водители не получат заказы, пока не будут созданы подтверждённые записи.**

## Миграция

Применить после проверки резервной копии и только при согласованном развёртывании: `alembic upgrade head`. Новая таблица — `legal_dispatch_verifications`. Никакие миграции на VPS не запускались.

## Откуда берутся записи

Новая таблица предназначена для *результата официальной проверки*, а НЕ для самостоятельного подтверждения водителем. Значения по умолчанию `false`. В этом выпуске **нет** интеграции с федеральными/региональными реестрами и **нет** интерфейса администратора для утверждения результата. Не заполняйте все флаги `true` ради разблокировки заказов: это создаст ложную юридическую уверенность. Требуется отдельная проверяемая процедура с источниками, временем получения, оператором и защищённым аудитом; срок действия должен учитывать сроки документов и актуальность реестра.

## Остаточные юридические риски

Модель не заменяет проверку требований 580-ФЗ, транспортного законодательства, страхования ОСГОП, 152-ФЗ, 54-ФЗ, действующих требований регионов и юридических документов. Не создаёт безусловной защиты от исков и не подтверждает легальность перевозок без реальных источников. Журнал согласий пока не интегрирован с мобильной авторизацией; он остаётся будущим этапом. Внешние изменения к действующему Backend не вносились.
