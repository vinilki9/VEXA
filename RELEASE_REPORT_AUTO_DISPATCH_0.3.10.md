# VEXA Taxi 0.3.10 — автономная диспетчеризация (исходники)

Дата: 21.11.2026. База: 0.3.9. Статус: подготовлен и проверен код; не выпуск production APK.

## Цель

Автоматическое распределение новых заказов **без нажатий диспетчера**. Клиент оформляет заказ; водитель самостоятельно принимает предложение и управляет фактическими этапами поездки. Диспетчер остаётся только для исключений, жалоб и ручного вмешательства.

## Реализовано в этом архиве

1. `backend/app/dispatch_engine.py`: считывает из БД `new` и `accepted`, начинает поиск, выбирает ближайшего подходящего водителя с онлайн-статусом и актуальным GPS, учитывая город, филиал, занятость, активность аккаунта и автомобиля; сохраняет предложение в БД; не создаёт дубликаты при повторном запуске.
2. `backend/app/dispatch_worker.py`: отдельный процесс, опрашивающий очередь в PostgreSQL; после рестарта восстанавливает работу по состоянию БД. Не зависит от HTTP-запросов диспетчера.
3. Тайм-ауты и отказы: после отказа водителя предложение переходит следующему; просроченные предложения закрывает worker; если никто не найден в пределах `DISPATCH_SEARCH_TIMEOUT_SECONDS` (по умолчанию 180 секунд), заказ становится `no_driver_found` и не создаёт финансовые начисления. Последнее уже отправленное предложение не прерывается, пока не истечёт его собственное время.
4. Блокировки строк заказов и частичный уникальный индекс `uq_driver_order_offers_one_pending_per_driver`: защищают от повторных предложений одному водителю при нескольких параллельных заказах. Миграция `0016_dispatch_pending_offer_uniqueness.py`.
5. В VEXA Client добавлен статус «Поиск водителя» / «Свободных машин не найдено», а финальный статус позволяет оформить новую поездку. История отображает «Машина не найдена».
6. В ответах Driver API убрана подсказка о необходимости ожидать ручного назначения диспетчером. Прямой отказ водителя также соблюдает общий лимит поиска.
7. Отдельный `dispatch_worker` предусмотрен в `infrastructure/docker-compose.yml` и `infrastructure/compose.production.yml`; примеры параметров в `.env.example` и `.env.production.example`.

## Сценарий

```text
Пассажир оформил заказ -> new
  -> dispatch_worker запускает поиск -> accepted
  -> GPS + занятость + филиал + активная машина -> предложение водителю
      -> водитель принимает -> assigned
          -> водитель прибыл -> arrived
          -> поездка началась -> in_progress
          -> водитель завершает -> completed -> финансовая запись (при выполнении правил оплаты)
      -> отказ / истёк ответ -> следующий подходящий водитель
      -> никого нет -> ожидание новых водителей до общего срока поиска
      -> срок истёк -> no_driver_found -> завершение без начислений
Пассажир может отменить заказ до назначения -> cancelled
```

## Проверки

- Новые тесты `backend/tests/test_automatic_dispatch.py`: 11 успешных SQLite-интеграционных сценариев (запущены с **временной тестовой заглушкой только для отсутствующих в среде библиотек авторизации**). Тесты используют настоящие функции автопоиска и БД; заглушки в исходники приложения не добавлены.
- Отдельно прошли 37 существующих проверок и 9 дополнительных subtests (`test_passenger_order_cancel`, `test_driver_status_retry_contract`, `test_additional_features_0_3_8_contract`, `VEXA_MAP/tests/test_map_server`).
- Alembic показывает единственную целевую миграцию `0016_dispatch_pending_offer_uniqueness` как `head`.
- Реальный PostgreSQL под нагрузкой, мобильные APK, веб-панели, Docker Compose и VPS **не проверялись**.
- Из-за отсутствия доступа к загрузке зависимостей тестовый запуск модулей авторизации в этой среде невозможен: `python-jose` и `passlib` отсутствуют. Production-режим должен содержать их из `backend/requirements.txt`.

## Перед переносом на реальный сервер

1. Создать резервную копию PostgreSQL с процедурой проверки восстановления. Не менять живую базу без согласования.
2. До миграции проверить существующие одновременные `pending` предложения одному водителю. При дубликатах миграция остановится — исправить историю предложений осознанно, не удаляя финансовые данные:
   ```sql
   SELECT driver_user_id, COUNT(*) FROM driver_order_offers
   WHERE status = 'pending' GROUP BY driver_user_id HAVING COUNT(*) > 1;
   ```
3. Выполнить `alembic upgrade head`, поднять один экземпляр `dispatch_worker` рядом с Backend, включить мониторинг его логов. Production запуск — только PostgreSQL.
4. Проверить на **двух и более реальных Android-устройствах**: два заказа и один водитель, параллельное принятие, обрыв GPS, отказ, истечение предложений, отмена, завершение поездки, повторное подключение, финансы.
5. Завершить проверки автомобильного класса и дополнительных услуг, фактического ETA/дорожного расстояния, корректности при множестве филиалов, снятие водителя с линии во время предложения, push-уведомления. Текущее ранжирование — по расстоянию по прямой (Haversine), затем рейтингу; не дорожный ETA.
6. **Безналичная оплата (карта/СБП) и выплаты не подтверждены реальными платёжными провайдерами.** Не считать текущую бухгалтерскую запись подтверждением поступления денег. Требуется интеграция и проверка идемпотентности транзакций перед публичным запуском.
7. Процент комиссии в коде зависит от рейтинга (4–10%), хотя исходная спецификация VEXA задаёт базовые 10%. До production требуется отдельное согласование модели и финансовые тесты.
