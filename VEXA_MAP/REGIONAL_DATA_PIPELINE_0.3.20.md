# VEXA MAP 0.3.20 — подготовка настоящих данных по федеральным округам

**Статус:** инструменты подготовки исходников, а не готовые карты России. Публикация, передача на телефон, GPS-навигация и установка на сервер отдельно. Windows, VPS, GitHub не изменены.

## 1. Регионы и источники

По согласованной географии VEXA MAP поддерживает восемь округов, отдельные OSM-выгрузки Geofabrik, и такие идентификаторы мобильных пакетов:

| VEXA ID | Geofabrik slug | Округ |
| --- | --- | --- |
| `central` | `central-fed-district` | Центральный |
| `northwestern` | `northwestern-fed-district` | Северо-Западный |
| `southern` | `south-fed-district` | Южный |
| `north-caucasus` | `north-caucasus-fed-district` | Северо-Кавказский |
| `volga` | `volga-fed-district` | Приволжский |
| `ural` | `ural-fed-district` | Уральский |
| `siberian` | `siberian-fed-district` | Сибирский |
| `far-eastern` | `far-eastern-fed-district` | Дальневосточный |

Файлы вида `https://download.geofabrik.de/russia/central-fed-district-latest.osm.pbf` — исходные OSM-объекты, **не** MapLibre `.mbtiles` и **не** граф OSRM. Путь `.../russia/<district>/<district>-latest.osm.pbf` был неверным и исправлен в `tools/fetch_osm_region.ps1`. Актуальность и доступность каждого URL необходимо проверять при загрузке. Источник: https://download.geofabrik.de/russia/ .

Внимание: данные OpenStreetMap распространяются по ODbL; необходимо сохранять атрибуцию OpenStreetMap и Geofabrik и выполнить обязательства ODbL при распространении производных баз данных. Проверяйте права на все сторонние слои, шрифты и спутниковые изображения отдельно.

## 2. Последовательная обработка при лимите 250 ГиБ

**Каждый раз только один округ.** Сначала скачать один `*.osm.pbf`, выполнить конвертацию, проверить результат, выпустить версию, затем удалять промежуточные файлы вручную после резервной копии и только потом переходить к следующему округу.

Структура, которую создаёт инструмент **при явном `--execute`**:

```text
VEXA_MAP/data/
  osm/                               # скачанный исходный *.osm.pbf
  builds/
    .central-2026.11.pending/        # временная изолированная сборка
      map.mbtiles                    # векторные MapLibre PBF внутри MBTiles
      tilemaker-store/               # временная дисковая БД Tilemaker
      osrm/region.osm.pbf            # отдельная копия OSM для OSRM
      osrm/region.osrm*              # серверные файлы графа MLD
      vector.log
      routing-extract.log
      routing-partition.log
      routing-customize.log
    central-2026.11/                 # результат только после успешных проверок
      map.mbtiles
      osrm/...
      build-receipt.json
```

Оценка расхода диска в `--plan` **приблизительная** (до 24 размеров входного PBF при OSRM, с минимальным запасом). Это не гарантия: реальные файлы могут занять существенно больше. Во время сборки инструмент периодически следит за объёмом staging и остатком свободного диска; при превышении лимита прекращает внешнюю команду. Оперативную память и время работы при этом не гарантирует. Стандартный бюджет 250 ГиБ, резерв 15 ГиБ. На диске, где свободно меньше, выполнение блокируется предварительной проверкой. Нельзя одновременно хранить все регионы и их временные копии без отдельного расчёта.

## 3. Подготовка исходного OSM.PBF на Windows — в будущем

Только по желанию пользователя на Windows с PowerShell:

```powershell
.\tools\fetch_osm_region.ps1 -District central-fed-district
```

Скрипт скачивает **только один** округ в `VEXA_MAP\data\osm`, пишет временный `.partial` и переносит результат на конечное имя лишь после проверки. Параметр `-ExpectedSha256` позволяет сверить заранее полученную достоверную сумму. Загрузка сотен мегабайт/гигабайт **не запускается** этим архивом автоматически. Сами `.osm.pbf` в ZIP отсутствуют.

## 4. Подготовка векторной карты и серверного дорожного графа

Необходимы установленные локально `Python 3.10+`, **Tilemaker** с открытыми ресурсами `config-openmaptiles.json` / `process-openmaptiles.lua` и, для серверного автомобильного маршрута, **OSRM** с профилем `car.lua`. Подбирать совместимые версии и проверять лицензии этих ресурсов нужно при установке. Сам VEXA не подгружает произвольный код из сети. Официальные материалы:

- https://github.com/systemed/tilemaker/blob/master/docs/RUNNING.md
- https://github.com/Project-OSRM/osrm-backend

Из корня `VEXA-deploy`, после размещения внешних инструментов:

```powershell
# БЕЗ сборки: только план/предварительная оценка — предпочтительный первый запуск
python VEXA_MAP/tools/build_region_0320.py `
  --region central --version 2026.11 `
  --pbf VEXA_MAP/data/osm/central-fed-district-latest.osm.pbf `
  --tilemaker-config C:/tilemaker/resources/config-openmaptiles.json `
  --tilemaker-process C:/tilemaker/resources/process-openmaptiles.lua `
  --osrm-profile C:/osrm/profiles/car.lua

# Выполнять лишь после ознакомления с оценкой диска, подтверждения реальных входных данных
# и установки бинарных инструментов. Это тяжёлая, долгая локальная операция.
python VEXA_MAP/tools/build_region_0320.py `
  --region central --version 2026.11 `
  --pbf VEXA_MAP/data/osm/central-fed-district-latest.osm.pbf `
  --tilemaker-config C:/tilemaker/resources/config-openmaptiles.json `
  --tilemaker-process C:/tilemaker/resources/process-openmaptiles.lua `
  --osrm-profile C:/osrm/profiles/car.lua `
  --execute
```

Если пока нужен только векторный MBTiles, **опустите `--osrm-profile`**. Отдельный `--tilemaker-bin` или `--osrm-prefix` позволяет указать подготовленные бинарные файлы. Для явно подтверждённого хеша можно использовать `--expected-sha256 <64 шестнадцатеричных символа>`; это предотвращает сборку из файла, не совпадающего с проверенным источником.

`--execute` не загружает PBF из сети, не публикует пакет, не затрагивает действующий сервер и не заменяет предыдущую версию. После ошибки папка `.pending` и журнал остаются для разбора, дальнейший запуск с тем же именем защищён от перезаписи. Для нового выпуска выбирайте новую версию; очистка `.pending` — отдельное осознанное действие оператора.

## 5. Что получаем, чего пока нет

**После настоящей успешной обработки** появится `map.mbtiles` в формате `metadata.format=pbf` с дорожным слоем `transportation`/`road`, а при указании OSRM — подготовленные **серверные** файлы графа. `prepare_vector_mbtiles.py` проверит совместимость слоёв и впишет ID округа. В `build-receipt.json` будут SHA-256 исходного PBF и итогового MBTiles. Это не цифровая подпись и не подтверждение достоверности источника. Геоданные поступают в архив только после отдельного законного импорта.

**Не включено в этот выпуск:**

- Скачанные OSM/PBF/MBTiles/геобазы по России — в текущем проекте их нет.
- Локальные SDF-глифы MapLibre: их нужно законно подготовить и импортировать через `--glyphs-dir`; без них русские подписи в офлайн-режиме могут не появиться.
- Полноценный индекс адресов и домов: `prepare_offline_navigation.py` по-прежнему принимает подготовленные оператором CSV. Tilemaker сам по себе не создаёт этот SQLite-индекс VEXA.
- Мобильный **полноценный** дорожный движок. OSRM MLD из этой сборки предназначен для серверного процесса. Файлы OSRM **нельзя просто скопировать в Android и считать маршрут готовым**.
- Сшивка федеральных округов, ограничения переходов, проверенные геоданные на границах округов, GPS map matching, TTS, ETA в реальном времени и тесты настоящей навигации.
- Спутниковые изображения/3D-рельеф. Они требуют отдельных лицензированных источников и ресурсов.

После обработки отдельно вручную копируют **проверенный** `map.mbtiles` в `VEXA_MAP/data/regions/<region>.mbtiles`, добавляют разрешённые глифы/адресную базу и публикуют новый манифест через уже существующий `publish-region`. Действующая карта не должна заменяться на телефоне до полной проверки контрольной суммы. Граф OSRM устанавливается отдельным этапом, только на выбранном сервере. Этот скрипт **ничего не публикует**.

## 6. Сохраняем продуктовые требования

- **Client:** строго вид сверху, `pitch=0`, без 3D.
- **Driver:** выбор 2D / наклонная 3D-камера, здания только при наличии геометрии/высоты.
- **Цвета:** графитовая основа, приглушённая бирюза интерфейса, яркая бирюза линии маршрута.
- **Данные:** независимые округа, установка после проверки SHA-256, офлайн-использование без обязательной авторизации.
- **Архитектура:** VEXA Backend не выполняет тяжёлую предобработку; SFTP и S3-совместимое хранилище — будущая унифицированная инфраструктура доставки.
