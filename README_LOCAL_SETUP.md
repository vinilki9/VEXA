# VEXA Taxi 0.3.5 — запуск на локальном компьютере

**Статус:** подготовленный исходный проект, НЕ проверенная производственная система. APK не собраны, реальных карт и маршрутизатора России в архиве нет.

## Начало работы (Windows + Docker Desktop)

1. Распакуйте ZIP на локальный диск. Установите Docker Desktop с WSL2, Python 3.12+, Android Studio/JDK 17. Для сборки Android потребуется загрузка SDK/Gradle-зависимостей.
2. Из папки `VEXA-deploy` выполните `Copy-Item .env.example .env` в PowerShell и заполните **двумя независимыми безопасными секретами** `POSTGRES_PASSWORD` (тоже в `DATABASE_URL`) и `SECRET_KEY`. Настоящий `.env` не добавляйте в Git.
3. Выполните `powershell -ExecutionPolicy Bypass -File .\tools\configure_local_ip.ps1` — сценарий применит обнаруженный LAN IPv4 к обоим Android-проектам и при наличии `.env` к адресу API. IP нужно проверить в выводе команды; эмулятор вместо него может использовать `10.0.2.2`.
4. Выполните `docker compose -f infrastructure/docker-compose.yml up -d --build` для PostgreSQL, Redis, автоматических миграций Alembic, API, диспетчерской, админки и локального VEXA MAP. До загрузки карт VEXA MAP отвечает, но `map_ready=false`.
5. Проверка на ПК: `powershell -ExecutionPolicy Bypass -File .\tools\check_local_system.ps1`; диспетчерская `http://127.0.0.1:8081`, администратор `http://127.0.0.1:8082`, карта `http://127.0.0.1:8090/health`, API `http://127.0.0.1:8000/health`.

На телефоне и компьютере должна быть одна доверенная Wi-Fi-сеть. Windows Firewall должен допускать обращения из локальной сети только к необходимым тестовым портам 8000, 8081 и 8090. Не делайте проброс портов в интернет и не ставьте debug APK публично. **Для release APK нужен HTTPS**, HTTP в релизном манифесте запрещён.

## Данные для карт и маршрутов

**Растровая карта:** импортируйте законно полученные растровые MBTiles в `VEXA_MAP/data/regions/*.mbtiles`. Для начала достаточно одного небольшого региона. Это не OSM.PBF, а готовые рендеренные картографические тайлы; генерация MBTiles из PBF ещё не автоматизирована. VEXA MAP читает несколько пакетов с одинаковым форматом и публикует URL стиля `/style.json`, а Dispatcher обращается к нему через свой `/maps/style.json`. После добавления файлов нужно перезапустить контейнер `vexa_map`.

**Маршруты:** `tools/fetch_osm_region.ps1` скачивает *исходную* региональную выгрузку, а `tools/prepare_osrm_region.ps1` подготавливает из неё дорожный граф OSRM. Затем задайте в `.env` `VEXA_MAP_OSRM_URL=http://osrm:5000`, `OSRM_BASE_URL=http://osrm:5000`, запускайте `docker compose -f infrastructure/docker-compose.yml --profile routing up -d osrm vexa_map api`. Это пока граф только выбранного округа, не всей страны.

**Поиск:** CSV `name,latitude,longitude` можно импортировать в `VEXA_MAP/data/places.sqlite` по инструкции `VEXA_MAP/README.md`. Для настоящего адресного поиска нужна качественная полная база домов/улиц.

## Android

Откройте `android/client` и `android/driver` по отдельности в Android Studio, выполните Gradle Sync и `assembleDebug`, затем проверьте экран карты, поиск адресов и маршрут с работающими сервисами. ## Совместимость Client / Backend / Driver (0.3.2)

- Client запрашивает конкретный заказ через `GET /api/v1/passenger/orders/{order_identifier}` с Bearer-токеном. Принимается UUID или публичный номер; Backend проверяет принадлежность заказа текущему пассажиру. Это устраняет зависимость статуса от первых 50 записей истории.
- Driver отправляет смену статуса на `POST /api/v1/driver/orders/{order_id}/status`. Backend принимает `order_id: UUID` (не строку) и проверяет переходы `assigned → arrived → in_progress → completed`.
- Если после завершения заказа не удалось прочитать кошелёк, Driver не сообщает ошибочно, что завершение не выполнено. При сетевой ошибке статуса список заказов перечитывается, поскольку ответ мог потеряться уже после подтверждения сервером.
- Оба Android-проекта используют параметр `vexaCityCode=obolensk` в `gradle.properties` (можно изменить на реально активный код города Backend). Это **не** заменяет будущий выбор города пользователем и не снимает ограничение Backend для города с несколькими активными филиалами.
- Для проверки: `PYTHONPATH=backend python -m pytest backend/tests/test_mobile_integration_contract.py backend/tests/test_pricing.py backend/tests/test_routing.py backend/tests/test_routing_providers.py backend/tests/test_route_pricing.py` из корня проекта. Полные интеграционные тесты Backend требуют установленных зависимостей из `backend/requirements.txt` и тестовой БД.


## Проверка входа диспетчера и администратора (локальная сборка)

1. После `docker compose -f infrastructure/docker-compose.yml up -d --build` откройте `http://127.0.0.1:8081/` (диспетчер) и `http://127.0.0.1:8082/` (главный администратор). Пути JavaScript/CSS относительные, поэтому страницы открываются и с отдельных портов, и под префиксами `/dispatch/`, `/platform-admin/` через внешний Nginx, настроенный в `infrastructure/nginx-vexa.conf.example`.
2. Для входа нужны **разные права** в базе: активный профиль `DispatcherProfile` для диспетчера и запись `PlatformAdmin` для администратора. Учётные записи и пароль необходимо создать безопасным способом в локальной базе; проект **не** создаёт универсального пароля по умолчанию.
3. После логина диспетчер использует `GET /api/v1/dispatch/auth/me`, а администратор — `GET /api/v1/platform-admin/auth/me`. Профиль администратора проверяется отдельно от доступа к списку организаций. Другие типы токенов не должны предоставлять доступ к панели администратора.
4. Проверка на компьютере: `powershell -ExecutionPolicy Bypass -File .\tools\check_admin_portals.ps1` — проверяет `200` и что JS-файл отдаётся с правильным типом содержимого. Убедитесь также, что URL, прописанные в `<script src>` итоговых HTML, возвращают JavaScript, а не HTML-страницу. Наличие `200` у формы **не подтверждает** работоспособность авторизации и БД — войдите тестовыми учётными записями с нужными ролями.

Эти изменения проверяются по исходникам и тестами. Работа на пользовательском ПК не подтверждена, пока Docker-контейнеры и база там не запущены.

## Обновление 0.3.4

- Backend: повторный POST водителя с тем же уже установленным статусом отвечает успешно без повторной финансовой операции или дублирования журнала.
- При переходе с 0.3.3 понадобится повторно войти в диспетчерскую, если сохранённый токен не содержал тип `dispatcher`.
- Client: на `401/403` прекращает повторный опрос заказа до новой авторизации; используется `BuildConfig.VEXA_CITY_CODE`.
- Driver: при смене аккаунта и после принятия/отклонения предложения кэш старых предложений очищается.
- VEXA MAP: проверяет, что координаты и данные OSRM имеют допустимые конечные числовые значения.

Установка Windows 11 отложена; изменения исходников сами по себе не запускают контейнеры на ПК.

## Обновление Driver 0.3.7 — «ДЕНЬГИ» и настройки

На главном экране Driver в карточке «Финансы» добавлена кнопка **ДЕНЬГИ** (вместо «Открыть»). Она открывает имеющийся финансовый экран; данные по-прежнему берутся из Backend, а не из тестовых значений. Финансовый экран учитывает выбранную тему оформления.

По кнопке ⋮ справа сверху открываются настройки водителя: оформление, параметры уведомлений о заказах, громкость, вибрация, сопровождение GPS, разрешения Android и выход из аккаунта. Код подготовлен, но фактическая сборка Android в текущей среде не выполнена из-за недоступного сервиса загрузки Gradle; см. `RELEASE_REPORT_DRIVER_SETTINGS_MONEY_0.3.7.md`.
