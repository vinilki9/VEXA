## Перед первым запуском

Уже настроенный VPS: `/opt/vexa`, пользователь `vexa-deploy`, GitHub `vinilki9/VEXA`, SSH Deploy Key, четыре GitHub Secrets (`VPS_HOST`, `VPS_USER`, `VPS_KNOWN_HOSTS`, `VPS_SSH_KEY`). Ubuntu, Docker, Compose должны быть установлены. Убедитесь, что скомпрометированный ключ заменён. Доступ к Docker эквивалентен root: ограничьте доступ к main и окружению production доверенными участниками; желательно требовать approval. Не отправляйте ключи или пароли в чат.

1. Отключите старый workflow через GitHub Actions, если он включён; убедитесь, что выполняющихся деплоев нет. В консоли VPS под root выполните `rm -f /opt/vexa-deploy/enabled`.
2. Распакуйте архив на Windows и перенесите **содержимое** папки `VEXA-deploy` в рабочую копию существующего репозитория GitHub. Включите скрытые папки `.github` и `.gitignore`. Сохраните историю Git, не используйте force push. Не загружайте `.env`, ключи, базу, keystore, `node_modules`, большие геоданные или APK. В репозитории должен остаться один активный workflow автодеплоя (`.github/workflows/deploy.yml`). Проверьте другие старые workflows вручную.
3. Зафиксируйте изменения в `main`, затем на VPS под root:

```bash
sudo -u vexa-deploy -H env GIT_SSH_COMMAND='ssh -i /home/vexa-deploy/.ssh/vexa_github -o IdentitiesOnly=yes -o StrictHostKeyChecking=yes' git -C /opt/vexa pull --ff-only origin main
```

При конфликте или расхождении веток остановитесь, не делайте reset. Убедитесь, что `cat /opt/vexa/VERSION` выводит `0.3.42`.

4. Установите скрипты, случайные секреты (если `.env` отсутствует), ежедневный таймер резервного копирования, проверку состояния каждые 5 минут:

```bash
bash /opt/vexa/tools/setup_vps.sh
```

Существующий `.env` не перезаписывается, но проверяется. Не меняйте пароль PostgreSQL простой заменой `.env` у уже существующей базы. Порты TCP 80/443 должны быть открыты извне, 22 — доступен для GitHub Actions/SSH. Не включайте Nginx на тех же портах. Не отключайте TLS. Публичный сертификат для IP выдаёт Caddy через ACME shortlived, выдача и продление ещё не проверены. Проверьте `free -h`, `df -h /`, `ss -lntp`. Для текущего VPS 1 ГБ RAM + 2 ГБ swap и 20 ГБ диска — тестовый режим; CI не отправляет образы при менее чем 5 ГиБ свободного места. Рекомендуется 4–8 ГБ RAM, 2–4 vCPU, 60–80 ГБ диска для первых нагрузочных тестов.

5. Когда setup завершится без ошибок, разрешите автодеплой:

```bash
touch /opt/vexa-deploy/enabled
```

Включите workflow обратно и откройте GitHub → Actions → VEXA Auto Deploy → Run workflow → main → Run workflow. При первом запуске GitHub устанавливает зависимости, выполняет статические, map и Backend тесты, формирует lockfiles, собирает 4 образа, запускает чистую PostgreSQL и применяет миграции дважды, проверяет API, синтетическую авторизацию администратора и конфигурацию Caddy. Только после успеха передаёт образы по SSH и запускает VPS. Не нужно устанавливать Docker на Windows. Результат каждого шага смотрите в Actions. Если тест/сборка не проходит, исправляйте ошибку, не отключайте проверку. Сгенерированные `package-lock.json` доступны как артефакт `web-lockfiles`: после успешного разрешения зависимостей добавьте оба в Git; при наличии lockfile используется `npm ci`. Здесь lockfiles не сгенерированы из-за отсутствия доступа к npm.

## Обновления и откат

После установки push в main запускает CI. На VPS больше нет сборки приложений: образы маркированы SHA и передаются через SSH без отдельного registry token. Существующие DB/Redis не пересоздаются при обычном обновлении. Перед миграциями сервисы, пишущие данные, останавливаются, создаётся дамп с проверкой списка архива и SHA256. Возможен кратковременный простой. Если миграционный revision не изменился и существует предыдущий успешно развёрнутый релиз, скрипт пытается вернуть его образы и сохранённый compose/Caddyfile. Если revision изменился, приложение остаётся остановленным для ручного восстановления. Сравнение revision не доказывает совместимость всех изменений данных/конфигурации; не меняйте исторические миграции. Автоматического восстановления поверх рабочей БД нет. Обновления инфраструктурных образов планируются отдельно после резервирования. Для остановки новых деплоев удалите `/opt/vexa-deploy/enabled`; уже начатый процесс это не отменит.

Резервные копии в `/opt/vexa/backups`, ежедневный таймер 03:15 UTC, хранение минимум 7 копий, удаление более старых 14 дней только после новой проверенной копии. Скопируйте за пределы VPS в защищённое хранилище, иначе потеря диска уничтожит и backup. Для тестового восстановления на отдельную БД:

```bash
sudo -u vexa-deploy -H bash /opt/vexa/tools/restore_test.sh /opt/vexa/backups/ИМЯ_ДАМПА.dump
```

Требует свободного места; тестовая БД не удаляется автоматически. Не использовать `docker compose down -v` на VPS. При нехватке места сначала проверить `docker system df`; не удалять образы активной и предыдущей версии. Проверка здоровья каждые 5 минут пишет результат в systemd journal, внешние уведомления и полноценный мониторинг нагрузки не подключены.

## Android и карты

Android Studio: открывать `android/client`, `android/driver` отдельно. JDK 17, SDK 35, Gradle 8.13; адрес API/карты уже задан. APK не собраны. Карты России, адресный индекс, офлайн-пакеты и граф OSRM отсутствуют; загрузить из отдельного хранилища. Не включать публичную раздачу больших пакетов на слабом VPS. Если подготовлен OSRM-граф, нужен отдельный запуск профиля routing, обе настройки URL должны совпадать; на текущем VPS не рекомендуется. Проверка доступности сервиса не означает готовность карты. Изоляция организаций, оплата, полный заказ и навигация требуют отдельного сквозного теста.
